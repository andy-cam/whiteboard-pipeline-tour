Add new ideas from anywhereNo napkin required.

A single command makes adding a new idea or task into the backlog fast and frictionless — a title or short sentence is all we need, and we even check for duplicates before adding.

Agent gives the ticket a work type and T-shirt sizing (XS–XL) — every size has a tailored route through the pipeline.

XS and S tickets skip this step.

L and XL tickets get carefully sliced into discrete, focused child tickets that comprise it — and dependencies and links get mapped now, not inferred later.

03aProve↳fires automatically: /test-plan

Complete test plans, built upfrontHow we'll know it actually works.

A detailed test plan declares a verifiable check on all acceptance criteria, and flags the types that call for a human review.

03bAttack@red-team

A hostile reviewer attacks the plan 'til it's pristineFeedback: breakfast of champions.

A pedantic reviewer agent tries to poke any holes it can in the plan — fixing flaws now before they become costly bugs later.

Reviewer can't see the author's rationale or edit the plan — no external influence, no shortcuts or mistakes silently made.

Capped to 2 rounds, human makes calls to resolve a plan that's churning.

04aBuildrun by a person: /ticket-build

Work gets routed to the right specialist agentBased on scope, not blast radius.

Small, single-scope work gets built directly. Medium work is handed to the specialist agent who owns that domain. Large and extra-large work first gets a plan splitting it by domain, then each piece goes to its right agent.

04bReview@security-eng · @qa-eng

Crucial reviews are triggered, not requestedI hope you like feedback.

Any work that touched a high-risk path (auth, payments, DB or API) or adds a new attack surface gets a mandated security agent review. Changes that are cross-domain, add a new pattern, or touch an API or schema summon the architect agent. Every ticket gets audited by the QA agent, with scope scaling to the ticket's size.

04cCommitlefthook

Nothing is committed until it clears our quality gatesFix that shit or you can't commit.

Shift left: stringent linting, formatting, secret, and typecheck scanners catch and resolve standards violations and recurring issues we added checks for, before they ever leave an engineer's machine.

04dShip↳fires automatically: /ticket-create-pr

Low-risk changes get an auto PRBut only if they meet the bar.

Six facts from the diff decide whether we let this lil' ticket raise its own pull request. Any uncertainty means no, so larger or riskier changes get handed to a human to decide if it's ready to pull request.

05aVerifyci.yml

CI smarts test only what might've brokenMake every Action Minute count (cause they ain't cheap).

Our continuous integration test suites that run on every change use what files changed to select the exact tests to enforce running.

Optimises build cost and CI build times without sacrificing confidence of quality.

05bVerify↳fires automatically: /test-run-pr

Bots go browsing for bugs to bashAll 4 corners, across all modes.

Every checklist item is run for real in a browser driven by Playwright, aiming to get manual human testing down to zero. And any visual test is checked at phone and desktop widths, in both light and dark modes — snapping screenshots as it goes so a human can follow along, then take over to complete any test plan items marked MANUAL (including any the agent couldn't verify).

10xAt scalerun by a person: /wave-planner

And we can run all that at once for an entire epic<Dramatic reveal SFX here>

A multi-tasking maestro is summoned when you kick off a build for an Epic or larger ticket, ready with a plan for how it would parallelise this work safely — using isolated worktrees, run in waves that manage sequencing and conflict risks. It even gives an estimate on how much faster you'll finish the build — typically 1.5x–2x as fast, but even hit 3x once! Foundations go first, so nothing starts before it can finish.

06Releaserun by a person: deploy-production

Humans handed the final product, to launch when readyAgents never even see a Prod deploy button.

Humans chose what to build, guided its journey through the agent pipeline, and verified it built what we expected. We remain in control of what gets released to Production, and only when we say so.

Keeping agents isolated from any way to break Prod is for their own good. And ours.

07Codifyhooks · checks · ADRs

Lessons learned become new rulesAgents that forget root cause are doomed to repeat it.

Agents keep track of defects and issues in memory, fixing novel single instances as they go.

When it spots a common occurrence, the agent offers to codify a new rule — a hook, an agent check, or a decision record — that catches it at build time and stops it from ever happening again.

08Shipped

Signed, sealed, delivered

This pipeline takes any idea, of any size or complexity, turns it into a properly specced work item, and creates a plan tailored for it to take the optimal path to Production.

It's designed to bake quality into the very foundations before any build even starts, balances managing cost with maximising velocity, and is driven by a handful of simple commands. No manual prompting steps or process guides to memorise.

✓Below the line

Eight key principles

Every one was earned rather than designed. They're listed in the order they'd be worth adopting.

  1. 1

    Measure, never self-report

    Confident declarations that nothing was missed are worthless. Let nothing but the tests do the talking.

  2. 2

    Author and adversary are never the same actor

    No self sign-offs, no influencing findings, no inverse incentives. The adversary gets the artefact to attack and the requirements only, with no editing access.

  3. 3

    A gate that never passes is not a gate

    With no written threshold, an adversary blocks everything, which tells you as little as rubber-stamping. Write down what a block must show.

  4. 4

    Fail closed

    Absence of a signal is not a pass. Print the reasons either way, so every refusal can be explained.

  5. 5

    Split the cheap half from the expensive half

    Opening a pull request can be undone; merging can't. Automate the first, keep a person on the second.

  6. 6

    Codify the lesson, not the fix

    The fix closes one instance. The rail closes the class. Put it at the earliest point the failure can be seen.

  7. 7

    One write path

    Every derived file has one source and one direction. The tooling refuses the wrong-way edit instead of trusting discipline.

  8. 8

    Context is the budget

    Cost grows with the square of session length, not with output. One task per session, and never wait by polling.

The project is a full operations platform for a services category. It's got a React customer booking site, a staff back-office, and shared API, all in a single TypeScript monorepo. This page shows how it gets built, not what it does.

I love this stuff but I'm not an expert, and would welcome any feedback on potential gaps or new ideas!

How it works · 01 Capture

Capture is cheap on purpose

/idea takes one sentence. It writes a plain-English title, searches open issues for a near-duplicate, opens a placeholder issue and sets its project fields. Nothing is planned or sized.

Specifying costs far more than capturing, so the two are kept apart. Ideas get specced later in batches with /spec-idea, when there's context to do several at once. An idea that has to arrive fully specified usually doesn't arrive.

  • Duplicate check. A near match gets linked instead of created.
  • Field completeness. No issue can be created without a priority and a milestone — the helper refuses. At capture these are placeholder defaults, so nothing lands untriaged; the real call is made at Specify.

How it works · 02a Specify

An interview, then a specification

/new-ticket classifies the work first (bug, feature, task, epic or decision) because the type fixes the shape of the issue. Bugs get reproduction steps and no acceptance criteria; features get criteria and explicit out-of-scope notes.

Then it interviews a person. Three to seven questions, tailored to the type — what job this actually does, who for, where the scope stops, what done looks like. Each one states why it matters and carries a recommended answer, so the reply can be a correction rather than an essay.

Only questions that would change the plan get asked; anything inferable from the codebase isn’t. Answers can open follow-ups, and the refined brief is read back for confirmation before a single specialist is consulted.

That interview is the specification starting to exist. What comes out of it becomes the ticket body: the job to be done, the acceptance criteria, the explicit out-of-scope notes, the affected areas.

Size (S, M or L) is recorded here and read again at Build, where it decides who builds the change and which reviews fire.

  • Confirmed brief. Nothing is planned, sized or written until a person has answered the questions and agreed the brief read back to them.
  • Verifiable acceptance criteria. Each one must be checkable at merge time and scoped to the ticket's own layer. "Works well" doesn't survive.
  • Real triage. Priority and milestone are decided here, not inherited. The milestone is checked against the live list of open ones, and an ambiguous call is put to a person rather than guessed.

How it works · 02b Decompose

Dependencies are declared, never inferred

Work too big for one branch becomes an epic with children. Children are only created once the parent is confirmed to exist, so a run that dies halfway leaves no orphans.

Blocked-by edges are registered as each child is created. Everything downstream reads them: ordering, parallel waves, and which children get closed at the end. By default every child is sliced from main; an integration branch is the exception, for children that must see each other before anything merges.

  • Parent exists. No child is created until its epic is confirmed.
  • Dependency registration. An unrecorded edge would be a silent scheduling bug, so edges are written at birth.

How it works · 03a Prove

The plan comes before the code

/test-plan writes at least one check per acceptance criterion and appends them to the issue as a checklist. @qa-eng authors it.

Acceptance criteria stay plain bullets on the ticket: they are the specification. The test plan below them is the checklist, and it is what gets ticked.

Every item is automated unless it falls into one of five categories: aesthetic judgement, a real third-party service, physical hardware, cross-browser behaviour, or tooling that doesn't exist. Everything else has to be driven by an agent in a real browser, even when that's fiddly.

  • Manual allowlist. An item can only be handed to a person if it names one of the five categories.

How it works · 03b Attack

Author and adversary are different seats

@red-team reviews the plan in a fresh context. It gets the issue and the artefact, never the author's reasoning, and it has no write or edit tools.

A reviewer who watched the plan being written inherits its author's frame and rationalises it. A reviewer that can edit the plan to fix issues could silently create much larger ones, if they mistook the intent. One that can easily fix what it finds could start finding only what it can cheaply fix (aka reward hacking).

  • Graded verdict. PASS, REVISE (applied with no second round) or BLOCK, and a BLOCK must name the concrete way a criterion ships broken behind a green suite.

The bar had to be written down. Before it was, the adversary blocked 9 of 9 reviews and every re-review blocked again, pushing median blocking time per ticket from 17.8 to 40.3 minutes. A gate that never passes tells you as little as one that always does.

How it works · 04a Build

Fourteen specialists, each owning a surface

/ticket-build routes by the size recorded at intake. Small: the orchestrator builds it. Medium: the one specialist who owns that surface. Large: @architect writes a plan, then specialists build in parallel by layer.

Boundaries are drawn by file path, not by skill. An agent that reaches its edge stops and names the owner instead of guessing across it, and ownership disputes land as numbered decision records.

@architect@frontend-ui@admin-ui@ui-system@domain-eng@ops-api-eng@data-eng@payments-eng@auth-eng@infra-eng@release-eng@security-eng@qa-eng@red-team

How it works · 04b Review

Reviews that fire on facts

@security-eng fires automatically whenever the diff touches the API, the database, auth, payments or cross-tenant access. It fixes directly or hands a fix spec back to the owner.

@architect reviews large tickets for structural drift. @qa-eng reviews coverage last: every criterion must map to a test or an allowed manual item. Untested work is unfinished.

  • Security triage. Triggered by path, so it can't be skipped by an agent that didn't realise what it touched.
  • Architecture review. Large tickets only.
  • Coverage review. Consulted last, never optional.
  • Local QA. The relevant suites run before anything is pushed.

How it works · 04c Commit

Twelve checks before every commit

Four are standard: a formatter and linter, markdown lint, a secret scan and a full typecheck. Eight were written for this repository: cookie attributes on cross-site sessions, banned legacy terms, raw brand tokens, em-dashes in content, brand drift, migration-journal order, and redaction guards on two credential helpers.

Each of the eight exists because a specific failure once got through with no error at all.

  • Pre-commit quality gate. A commit that fails any check doesn't happen.

How it works · 04d Ship

Measure, never self-report

Opening a pull request can be undone by closing it; merging can't. So an agent may open its own pull request, but only when a script, not the agent, says so.

The script checks facts: a feature branch, five files or fewer, one workspace scope, no migration, workflow, auth, payment, brand, secrets or lockfile path, a fully checked test plan, and the relevant suites passing, which it runs itself. The ticket's recorded size is ignored on purpose, because the diff is ground truth.

  • Straight-to-PR eligibility. Anything it can't determine counts as no, and it prints its reasons either way.
  • Only a person merges. The gate opens the pull request and stops there: a human reads the diff and decides, and an ineligible verdict stops and asks one.

How it works · 05a Verify

One required check over change-scoped suites

A should-run gate filters out noise, path filters raise a flag per area of the repo, and a selector picks only the suites those paths can affect.

Everything reports into one aggregating job, and that's the only check branch protection requires, so suites can be added or made conditional without touching the rule. The trade-off: when expensive suites skip on most PRs, an existing failure can stay hidden until a PR finally triggers that suite.

  • CI pass. The single required check for every merge.

How it works · 05b Verify

Nothing ticked without a recorded result

/test-run-pr reads the checklist off the pull request and runs every item. It signs in to the preview through a helper that keeps the password out of the model's context entirely.

Visual changes are checked at 375 and 1280 pixels, in light and dark, measuring every instance of the element and re-checking for horizontal overflow after each resize. Results are written to a file and the checkboxes on the ticket are updated from it, then a script re-checks its own work: any box it failed to tick is reported rather than passed over.

An unchecked manual item is visible on the ticket and holds it open. The pull request says refs instead of Closes, and the issue moves to Review so whoever is watching can see exactly what is left.

  • Every plan item resolved. An item that couldn't run blocks; silence is never read as success.
  • Four-corner verification. Both widths, both themes.

Single-mode checks have produced confident false greens. A green result only counts if you can say what would have made it red.

How it works · 10x At scale

Waves, worktrees, and what it costs

/wave-planner estimates each child's footprint, then classifies conflicts: the same file must be serialised, a shared consumer should be, and a declared dependency fixes the order. What's left is packed into the fewest waves.

Each change gets its own git worktree and headless worker, so no two agents share a checkout or a port. Worktrees are torn down by a script that stops their dev servers first, because deleting the folder orphans them.

Cost: context is re-billed on every request, so spend grows with the square of session length. Across 135 transcripts, about 70% of spend was re-reading history and about 10% was output. The lever is one task per session.

How it works · 06 Release

The last human sits on the irreversible step

Staging deploys on every merge. Production only starts when the operator enters a live TOTP (time-based one-time password) code from their own authenticator app, then runs a typecheck and build before touching anything.

The migration runs in a protected environment that exists to require a named reviewer's approval. The API deploy waits for it; the customer site and admin app don't. Then come canary checks and a rollback decision within 30 minutes, with recovery by point-in-time restore.

  • TOTP code. A person enters a live code from their authenticator app — one the agent never holds — so nothing dispatches by accident.
  • Protected-environment approval. A named person approves the migration: the one human approval left in the pipeline.
  • Forward-only migrations. Destructive changes need an expand-then-contract sequence or a recorded override.
  • Canary and rollback window. An explicit decision inside 30 minutes.

How it works · 07 Codify

Codify the lesson, not the fix

After every incident the question is: what would have caught this automatically? The answer becomes a rule the agent reads, a hook on the edit, a pre-commit check or a CI job, placed at the earliest point the failure can be seen.

For example, cross-site session cookies were being silently dropped by browser privacy rules. The response was accepted, the cookie showed in devtools, and every later request returned 401 with nothing in any log. That's now a committed check on every cookie the API sets.

  • Fix the workflow, not the run. When a workflow issues a command that fails every time, the workflow gets repaired, not just the current run.

How it works · 08 Shipped

The audit trail is the character

Every stamp on the box is a gate the change cleared: sized, split with its edges declared, a plan written and attacked, built by its owner, reviewed on the facts, committed through the interlock, a pull request earned, CI green, seen at four corners, merged in its wave, and approved by one person.

That's twenty-one named gates along the line. One of them needs a human.
